## Agents act only on the caller's own appointments (2026-10-13)

Phase 1 of the Nudge port. Nudge's 2026-10-11 entry ("Agents move and cancel
the contact's own meeting") read Resepta first and deliberately did not copy
three of its gaps; this entry closes them here.

**Found, in code.** `/retell/functions` (`convex/http.ts`) took the caller as
`args.phone ?? from_number`, so a phone number the model passed won over the
call itself: a caller who read out somebody else's number could have that
person's next appointment found, moved or cancelled, or details saved onto
their record. The legacy runtime MCP (`convex/voiceMcp.ts`) made `phone` a
required model argument on both of its tools for the same effect.

**Identity from the call leg.** `retell.callerOfCall` reads the customer's leg
by direction, with the org's dial code, never the business's own line: the
same reading `recordCall` makes after the call. It is resolved lazily, so
`check_availability` (the most frequent tool, which needs no caller) pays no
extra round trip. No usable number (hidden caller ID, web call, own line):
book, save and find/cancel/reschedule refuse with a sentence the agent can say,
and each tells it not to take a number from the caller instead. Booking refuses
too: that is Nudge's rule in `meetingTools.ts` (`caller-not-known`), and a
number read out loud is exactly what must not be booked against.

**The legacy MCP identifies nobody.** Its requests carry only the agent's
bearer token. Retell can template `{{call_id}}` into MCP headers, but the
agents still on this transport were published with an Authorization header
only, and the publish that could add one also strips these tools
(`withRuntimeSaveTool`). So `get_call_context` returns the business half (the
caller's card already arrives as ring-time variables) and
`save_customer_details` refuses; post-call analysis still fills missing values
from the call. Rejected: recording ringing calls to cross-check a typed
number, a new table and TTL for a transport that should be deleted once no
enabled agent predates template v10.

**Own appointment, judged at the moment of the change, six a day.** Both
lanes looked up "the next appointment" by phone or customer and then wrote to
whatever id that returned, and a move checked only that its START was not in
the past and fell inside opening hours, so it could land on a full slot, on
top of the customer's other booking, or half an hour into a lunch closure.
`convex/agentAppointments.ts` is now the one path for both: `ownNext` (the
customer's next open appointment in the org, how many more they have, the
day's change count), `checkMove`, and the two writes `moveOwn`/`cancelOwn`,
which re-read the target (still theirs, still next, still at `from`) and, for
a move, re-run the booking page's own helpers (now exported from `booking.ts`,
unchanged) inside the transaction that writes. One deliberate difference from
the page: an org with no opening hours set is bound only by its closures,
because the agents have always booked such a business at any time. The cap is
Nudge's six a day on `customers.agentChangesAt`: `voiceBook` counts every
booking and never refuses one, moves and cancels past it are refused. On the
phone the refusal also emails the team (`moveNeedsPerson`/`cancelNeedsPerson`
on the failed-send switch, `failedCalendarCancel`'s precedent), because the
agent has just promised that a colleague will be in touch and nobody is
reading a live call; in chat the model is told to call `escalate_to_staff`,
so the business's own handover setting decides what that means. The cal.com
lane keeps its order (cal.com first): ownership, the cap and the hours are
checked before cal.com is called, and the local write then lands with
`providerConfirmed`. `markCancelled`/`markRescheduled` now call the extracted
`cancelAppointment`/`rescheduleAppointment`, unchanged. Not taken from Nudge:
`find_my_meeting` listing move-to times (Resepta's agents already call
`check_availability` for that), and warning about the cap at find time, which
would promise a colleague without the email that backs the promise.

**A suggested reply changes nothing until it is sent.** `chatAgent.respond`
ran the same `executeTool` in every mode, so in suggest (and in shadow, which
never sends at all) the agent had already booked, moved, cancelled or saved by
the time a person saw the draft, and the booking rule had already messaged the
customer. Now, outside live, every write tool runs its checks and writes
nothing: a booking goes through `retell.previewBook` (the guards extracted out
of `voiceBook` as `bookingProblem`, so the write and the dry run share one
copy), a move through `agentAppointments.checkMove`, a save through the write
gate with `dryRun`. The change is recorded on the turn
(`chatAgentTurns.intents`, Nudge's `meetingIntentV` in Resepta's words) and
the tool answers as though it had happened, which is Nudge's choice: the
draft's words then become true at the moment they are sent. `sendSuggestion`
claims the draft, makes the changes in the model's order with each one
re-checked (the appointment must still be the customer's next one at the time
the draft named; a booking runs `startRefusal` and the whole booking path
again), and sends only if every one took. A refusal retires the draft with the
reason (`refuseSuggestion`) and the composer says why; a send that fails after
the change says that instead and puts the words back without the change
(`intentsAppliedAt`). Shadow turns keep their intents as the record of what
they would have done.

The UI part is one line above the composer ("Sending this books Tue 14 Oct,
14:00 · Saç kesimi"), in the business's timezone, with an × that drops the
change by retiring the draft. An attachment, a quote or a scheduled send cannot
carry a change, so the composer refuses those while one is pending, rather
than sending "you're booked" with nothing booked. Two things changed beside
it: the automation stand-down (`automationAnswered`) is live-only, because in
suggest nothing has fired yet and standing down would drop the request; and a
dry book, move or cancel tells the model when a business rule will send the
confirmation once the draft goes, so the draft stays short. Not taken from
Nudge: its Approve/Discard tray. Resepta's draft lives in the composer and can
be edited, so the change line and the × are the approval surface instead.

**Text beside a tool call is not a reply.** The chat loop kept
`finalText = result.text || finalText`, so whatever the model wrote in the
same completion as a tool call ("I've booked you in" next to a
`book_appointment` the tool then refused) became the reply whenever no later
round wrote text, and the round that hit `MAX_TOOL_ROUNDS` sent its text too.
Only a round with no tool call is an answer now; hitting the cap records
`tool-limit` and sends nothing.

**A booking asked for twice is one booking; every door has the same brake.**
A Retell retry after a slow answer, or a caller repeating "yes, book it",
reached `voiceBook` as a second booking for someone already holding that exact
minute and came back as `customer-busy` about their own appointment.
`voiceBook` (and `previewBook`) now return the open appointment at that minute
with `existing: true`, which both lanes turn into "they already had exactly
this booked", and a dry run records no change for it. An ASAP order has no
minute to match, so an open ASAP order with the same lines in the last five
minutes stands in. The booking page's five-open-bookings brake
(`MAX_UPCOMING_PER_PHONE`) moved to `lib/bookingLimits.ts` unchanged and is
now the first guard in `bookingProblem`, so the agents cannot stack bookings
the page would refuse. Known gap, parked lane only: on a cal.com org a retried
call still creates a second cal.com booking before `voiceBook` dedupes ours.

**An assistant's booking and cancel leave a feed row.** Staff bookings
(`schedule.ts`) and the office MCP (`agentTools`) wrote `appointment_created`,
and every move wrote `appointment_moved` through `rescheduleAppointment`, but a
booking by phone or chat wrote nothing, and `cancelAppointment` writes its
`appointment_status` row only when a person in the salon started the cancel.
`voiceBook` now writes `appointment_created` and `cancelOwn` writes
`scheduled → cancelled`. With no session on a call or a live chat they read
as the system; a drafted chat change a person sent carries that person.

**A WhatsApp delivery seen twice is one message.** `messages.logInboundRow`
inserted on every call, and only the shop phone's own replies were deduped
(`handleEvolutionEvent`), so a Meta retry or an Evolution replay of a
customer's message made a second bubble, emailed the staff again and
scheduled a second assistant turn that answered again.
`webhook.processInboundMessage`, the single entry for both lanes, now returns
before doing anything when a row in the same org already holds the message's
wamid. `by_wamid` spans every org, so the org is compared in code, and
`take()` rather than `unique()` keeps a historical duplicate from making every
later delivery throw. Two simultaneous deliveries serialise on the index
range, so the second one sees the first.

**The manage page counts against the same six.** Every move on
`/appt/<token>` re-sends the confirmation (`booking.reschedule` →
`scheduleConfirmationIfConfigured`), so a page left open under an idle finger
could message the customer as often as it was tapped. `booking.reschedule` and
`booking.cancel` now refuse with `too-many-changes` past the cap and count
each change on `customers.agentChangesAt`, the field the assistants use: one
person changing one diary, whichever door. The page says to call the business
(`booking.tooManyChanges`). That page's own slot rules are unchanged.

**The phone agent asks for a time, and a "no" comes with two that work.**
Chat's `check_availability` had a `time` parameter answered as a fact; the
voice tool had none, and its description still said "if the calendar is not
connected, ask for the caller's preferred time", which has not been true since
Resepta became the calendar. The voice tool now takes `time` (template v14:
a schema and description change, so Update reaches existing agents; the
matching prompt line in all three languages reaches new agents only, the
template rule) and both lanes answer it through `judgeRequestedTime`. A taken
or shut time, and any booking or move refused for its time, now carries
`nearest_free`: two free times either side from `retell.nearestFreeTimes`,
which walks the asked day and then outward (a week ahead, three days back)
using the booking page's own `freeStarts`, so whatever is offered the write
accepts. Nudge's `nearest` picks one on each side, not the two closest:
"Saturday at 11 or Monday at 9", never two versions of the same no. The
hours text now lists days Monday first (Nudge's `closedWeekdays` fix,
e180f855): "Saturday, Sunday", never "Sunday, Saturday".

**The sweep of the other LLM doors.** The office MCP (`mcp.ts` +
`agentTools.ts`) takes its org from the key and org-checks every id it is
handed; nothing there trusts a model for identity. Three defects were fixed
on the way. `voiceProvisioning.begin` took the new agent's inbound line as
given and only the provider-side bind checked it (refusing a line with an
inbound agent right now), so the app or `create_phone_agent` could bind a line
provisioned to another workspace, or one it dials out from; it now runs
`retell.lineUsable` first, like every reassignment. Undoing a
`publish_agent_prompt` republished the old prompt before `markUndone` checked
the action was the caller's own; the check now runs first. Undoing
`log_activity` deleted calls and messages without `recomputeThread`, leaving
the inbox summary naming rows that no longer exist. Not fixed, reported:
undoing `create_appointments` keeps only appointments with a linked message
although its comment promises to keep moved, cancelled and no-show ones too
(the journal row does not record their original state, so it cannot tell),
and undoing `create_customers` deletes customers who have calls or notes,
leaving those rows orphaned (customer deletion is the next phase's).

## Phone agent template v14, recogniser hints and the model guard (2026-10-13)

Phase P1c of the Nudge port: the pieces of Nudge's voice and LLM work that P1
did not cover. P1 had already bumped the voice template to v14 for its own
change, and nothing is pushed, so everything here folds into v14 and an owner
clicks Update once.

**A model pick in /admin could switch the assistant off, or switch the budget
off.** `lib/llm.ts` sent `output_config.effort` to every Anthropic model, and
the console's picker lists whatever the platform key reaches, Haiku 4.5
included, which refuses that field with a 400. The price table had no 5.5
rows either, so claude-opus-5-5 or claude-haiku-5-5 metered every turn at $0
and the monthly budget never closed. Nudge found both (08311abc). The table
is now `MODELS`, one row per model the key lists with its price and the
parameters it accepts (rates checked against Anthropic's pricing page today;
the OpenAI rows are Nudge's). Effort goes only where it is accepted, and Opus
4.6 to 4.8 and Sonnet 4.6 get the explicit adaptive switch, because left out
it means no thinking on those four. An unpriced model fails closed: the turn
skips as `model-unpriced` before any spend, the picker stops offering such a
model, and the org page's pill says why. Turns are priced per completion,
because Haiku 5.5 charges its long rate per request past 100K prompt tokens.
Rejected: letting an unknown model run and billing it at the dearest known
rate. The assistant would keep answering, but nobody would notice every
reply priced at Fable's rate; a skip with a reason shows up the same hour.
Not taken from Nudge: moving the default to Haiku 5.5. The default stays
claude-sonnet-5, which is Serdar's call to change.

**Template v14 gains a ceiling, a holding line and local times.** Three of
Nudge's voice changes, all tool or agent-doc fields so Update delivers them.
A call now ends at ten minutes (`max_call_duration_ms`, Nudge's value and
field, 7bf2c681); the template set no cap of its own, though its comment on
`canEndCall` names max_call_duration as the only backstop besides end_call.
The five calendar
tools speak while they run, with an instruction in the agent's own language
that allows a few words and no day or time (Nudge f2a44605: its holding line
said the time and the confirmation said it again). Before this only
check_availability and book_appointment spoke during execution, with the
provider's unlimited default instruction, and find, cancel and reschedule
left the caller in silence. `save_customer_details` stays silent, as v10
decided for a write that answers in a second mid-flow. And `start` on
book_appointment and reschedule_appointment is described as the business's
wall time, `YYYY-MM-DDTHH:MM` with no zone, the shape chat's tools already
use, where it said "an ISO 8601 timestamp", which invites a UTC answer.
The server keeps reading a stamp that carries an explicit offset as the
instant it names (Nudge's `parseStart` does the same). Nothing new names a
tool, the hazard Nudge ba2d956a recorded: answers are live for every template
version and descriptions arrive with their own tools; that is now a rule in
AGENTS.md. The Update banner's text named v11 to v13 improvements and
described nothing v14 does; it now says what v14 changes.

**A non-answer is never stored or read back.** The post-call analysis is told
to leave a field empty when the call did not mention it, and models write
"Belirtilmedi" or "Not specified" instead. `coerceVoiceValues` kept anything
non-empty, so the placeholder landed on the empty field, blocked every later
inference from filling it (post-call inference only fills missing fields),
and was injected at the next ring as a fact about the caller; in a name field
it became the greeting. On a picklist field the gate rejected it instead and
told the agent to ask the caller again about something never mentioned.
Ported Nudge's `lib/nonAnswer.ts` (3e61d794) with Turkish and German stems,
matched whole or with a qualifier on either side, because Turkish and German
put the verb last ("Görüşmede belirtilmedi"). It is dropped by the payload
normaliser, skipped by the write gate (where a stored placeholder now counts
as empty, Nudge's `mayOverwrite`), left off the call's own collected list,
refused as a booking name in both lanes, and hidden from the ring-time
injection and the chat lane's variables. "Yok", "None" and "Keine" are
non-answers only where a name is expected; for a clinic's allergy field they
are the answer, which is why Nudge's global "none" did not come across. Not
done: cleaning placeholders already stored. They stay on the customer card
until someone clears them and no agent reads them back, but a message
template's first-name token still would; with new ones blocked at every
write, that is a one-off cleanup rather than a growing problem.

**The recogniser hears the business's own words.** Nudge sets the provider's
`boosted_keywords` from its knowledge bases (3379705e) and learned, before
shipping, that its first build would have published an empty list over fifty
place names (61788709). The plan had skipped this for Resepta because Nudge's
lists live on bases that would sit in the one provider account every business
shares; the flip was that Resepta already holds the vocabulary as each org's
own rows. So the list is derived, never edited: the business name, then the
active team, then the active services in the owner's order
(`lib/boostedKeywords.orgKeywords`, read in `agentEditorContext` by org after
the agent is proven to be the org's). It rides every publish that already
writes the agent doc: the Update banner (`syncTemplate`, part of v14), the
prompt save (`publishViaDraft`, which now always writes the agent doc), the
fields publish, a rename and the webhook fix that ends provisioning. Nudge's
two lessons hold here as a merge rather than an adoption step:
`retellAgents.boostedKeywords` records what Resepta sent, the next publish
replaces only those words and keeps anything typed in the provider's
dashboard (on the first publish nothing is ours yet, so everything already
there stays), and a merged list that comes out empty is never sent. Capped at
fifty, under the sixty-one Nudge runs in production: the provider documents
no ceiling, and a list it refused would fail the whole publish, the owner's
prompt save included. Names go out as words: brackets and symbols become
spaces ("Saç kesimi (kadın)" on Bella is sent as "Saç kesimi kadın"), while a
word somebody else placed goes back exactly as written. Not done: a view of
the list on the agent page (it is derived, so there is nothing for the owner
to edit), and the engine-only toggles (hang-up switch, operator model
change) do not send it.

## The appointment hardening, review fixes (2026-10-13)

An independent review of "Agents act only on the caller's own appointments"
found six defects; each is fixed in its own commit.

*The line is judged when it is bound.* The `lineUsable` check added to
`voiceProvisioning.begin` judged the number the request asked for, but
`begin` resumes the newest unfinished job and keeps that job's number once its
agent exists, and the provisioning action bound `started.row.inboundNumber`
unchecked. A stale job holding a line since given to another business would
have bound it. The action now runs `lineUsable` for the number it is about to
bind, right before `bindInboundNumber`.

*"Already booked" means the same visit, and the agent stands down only on a
message that is really going.* `alreadyBooked` matched any open appointment
at the minute, so "add a beard trim at 14:00" to a 14:00 haircut answered
"they already had exactly this", and the chat result still said
`booked: true`, which tripped the live stand-down while `voiceBook` had
returned before scheduling anything: the customer got no reply at all. It
now matches the minute and the same services in any order; a different visit
there falls through to the customer's own clash (`customer-busy`, with its
remedy). `scheduleLifecycleMessages` returns how many customer messages it
scheduled, `voiceBook`, `rescheduleAppointment` and `cancelAppointment` pass
that up, both lanes put `confirmation_sent` on their answers, and the live
stand-down fires on that field alone instead of on "a booking rule exists".

*The cap stops the loop it was meant for.* The review showed a
cancel-and-rebook loop the count never stopped: a customer's own WhatsApp
cancel (typed İPTAL or the cancel button, `webhook.processInboundMessage`) was
neither counted nor capped, and assistant bookings were counted but never
refused. Decision (the coordinator's, applied as given): a customer's own
cancel COUNTS and is NEVER refused, on WhatsApp and now on the manage page too
(which had been refusing it past the cap since this morning); past the cap
the assistants refuse new BOOKINGS as well as moves and cancels and hand over
(`bookingProblem` returns `too-many-changes`; the phone lane emails the team
with the new `bookNeedsPerson`, chat calls `escalate_to_staff`). In the same
path a repeated İPTAL on an appointment already cancelled no longer sends the
cancellation again, and a cancel or confirm button is honoured only on the
tapper's own appointment: the payload names its appointment by id, and the
org check alone let one customer's tap reach another's booking in the same
business.

*Which appointment is the one the agent read back.* Cancel and reschedule took
`from` from `ownNext` in the same request and acted on whatever was next at
that moment, so a Retell retry, a second "yes, cancel it" or a model calling
the tool again turned "cancel A" into "cancel A, then B", and in the live lane
"book Wednesday, then cancel Friday" cancelled the new Wednesday. Both tools
now take `appointment_start`, the wall-clock start `find_appointment` /
`my_appointments` gave (`localMinuteIso`), and `agentAppointments` acts only on
the customer's own open appointment in that minute (`ownTarget`, `rowsAt`);
there is none, nothing moves (`appointment-changed`). A repeat is a no-op
answer: the row at that start is already cancelled, or already open at the
new time. `moveOwnTx`/`cancelOwnTx` are now plain functions (their mutations
wrap them) so the next fix can run several in one transaction, and
`writeOwnChange` finds the cal.com uid itself. Chat's tools changed at once
(template v10); the voice change is folded into the unshipped v14, and
`/retell/functions` reads `templateVersion` so an older engine is never told
to pass a parameter it lacks: it keeps "the next one", refused for three
minutes after any change, which covers a retry and a repeated yes.

*A draft's changes land together or not at all, and are judged together.* The
review's HIGH finding: sending a draft made its changes one transaction at a
time, so "book me Wednesday instead and cancel Friday" booked Wednesday (its
confirmation went), the cancel was then refused, the reply was dropped and
the composer said nothing had changed. And the dry run judged each change
against the calendar as it was, not as the draft's earlier changes would
leave it: "switch my Tuesday 14:00 haircut to a colour" recorded the cancel,
the book step found the haircut and returned `existing`, and sending
cancelled without rebooking. Now `voiceBook`'s body is `agentBookTx` and the
move and cancel are `moveOwnTx`/`cancelOwnTx`, plain functions, and
`applyIntentsTx` runs a draft's changes through them in one transaction.
Sending is `applyDraftChanges`: the first refusal throws a `ConvexError`
carrying the reason, the mutation rolls back whole, and `sendSuggestion`
turns the reason into the composer's message. The dry run is `simulateDraft`,
which calls `simulateDraftInner` (the same `applyIntentsTx`, then always a
throw) as a nested mutation and returns the verdict, so a draft is judged the
way sending will judge it. Before relying on that, a throwaway probe on the
local backend confirmed that a nested mutation's `ConvexError` reaches its
caller with its data, and that a job it scheduled before throwing is gone,
against a control that kept one. The review's scenarios were then run through
`simulateDraft` on a local customer with no appointments: a service switch at
the same time succeeds, the same visit twice returns `existing`, a different
visit at that minute is `customer-busy`, a booking followed by a cancel of
nothing refuses at the second change, repeated cancels and moves are no-ops,
and a seventh change is `too-many-changes`. Afterwards the customer had no
appointments, an untouched counter and no newly scheduled jobs. `previewBook` and the
save gate's `dryRun` are gone; nothing uses them. A cal.com booking or a
cal.com-held appointment cannot be changed inside a transaction, so a draft
refuses one.

## Deleting a customer deletes them (2026-10-13)

Phase P2 of the Nudge port (plan area 10). KVKK lets a person ask a business
to erase them, and "deleted" did not mean that here.

**Found.** `customers.remove` deleted the customer's appointments and the row,
and wrote their name into the `customer_deleted` activity row it left behind.
Everything else stayed, filed under an id that no longer existed: messages
(and the photos and voice notes those keep in our storage), calls with their
transcripts, notes, assistant turns, bulk-run items, inbox pins and read
marks, the activity rows about them, and the office-MCP journal rows holding
what a tool had written about them. No screen has ever called `remove` (it
dates from the first scaffold), so the doors that actually deleted customers
were the MCP undo of `create_customers` and the operator's
`voiceBackfill.removeOwnNumberContacts`, and both deleted the bare row.

**Built**, Nudge's footprint pattern (`contactFootprint`, 2026-09-16) adapted
to a deployment every business shares. `convex/customerDeletion.ts` holds one
`FOOTPRINT` list, grepped from the schema rather than remembered, that serves
both the preview's counts and the sweep, so what a person is shown is what
goes. Three indexes make every entry an index range: `inboxPins` and
`inboxReads` gained `by_org_customer` (pins and read marks are per person, and
an operator holds them without a membership, so walking the team would miss
some; Nudge added `by_lead` to both for the same reason), `bulkRunItems` the
same, and `messages.by_customer_status` lets the first step find exactly the
queued sends. The first step runs in the caller's transaction and makes the
person gone at once: the row is REPLACED by a blank carrying `deletingAt`,
the phone becomes `deleted:<id>`, the thread summary goes with the rest of the
row, queued sends are deleted (the cancellation `wa.cancelScheduled` already
uses), and up to 100 appointments are deleted, which also ends their
reminders. The sweep then pages through the rest, asserting `orgId` on every
row, deleting an inbound file from storage when neither the library nor
another message holds it, and deletes the row in the pass that finds every
table empty. Before any of that, a commit taught every reader what the mark
means: each WhatsApp, email and assistant context loader returns nothing for a
marked customer, a parked send or a retry is cancelled at claim time,
`messages.logOutQueued` refuses as the backstop, bulk runs and campaigns skip
them, lists, search, the record, the calendar, the call list, the manage-page
link and the MCP stop showing them, nothing can be attached to them, and
`writeThread` never puts their summary back.

Two departures from Nudge. Its sweep deletes a contact's activity rows; here
the activity log is the business's audit trail, so a row loses the customer
and appointment link and any free text (a status change and field names stay),
journal rows lose the values a tool wrote, and the deletion leaves one
`customer_deleted` row naming who did it and never whom. And Nudge's calls are
message rows, so it has nothing to say about late provider events; here the
analysis arrives on a second webhook minutes after a call, a webhook can be
retried, and `voiceEvents.recoverAnalysis` fetches a late analysis by itself.
Each would reach `retell.recordCall`, find no calls row and write the call back
with a new customer built from the transcript. The sweep replaces an erased
call's events with one `customer_deleted` marker (ids only), and `enqueue`,
`recordCall` and the recovery check it. Events still queued or failed under
the customer's number for a call that never got a row are matched by that
number and erased the same way.

Provider copies: Nudge deletes nothing at its providers and says so in its
preview; ported as that note, not as a provider call. The phone provider keeps
its recording and transcript of each call.

**Rejected.** Leaving the phone on the marked row and teaching each lookup to
skip it: there are twenty-odd `by_org_phone` reads, several with `.unique()`,
and a new customer created from the same number would make two rows match.
Finding queued sends through `by_org_status` in the first step: a running
bulk email holds hundreds of queued rows with their HTML, more than one
transaction should read for one customer. Dropping a message from the number
while the sweep runs: a person who writes again after being deleted is new
contact the business has to see. A cron to restart a stalled sweep: the sweep
only throws on a bug, and the restart is one command (documented in
subsystems). A delete button: the plan scopes this phase to the backend and
the connector, which is also how Nudge shipped deletion before its trash.

**Verified** on the local backend with a throwaway probe module (not
committed) in a dev workspace, Bursa Site Yönetim, not Bella. It seeded one
customer with a row in every footprint table: three messages (one queued for
next week, an inbound one holding a stored photo, an outbound one showing a
library file), a call with its processed event, a failed event for a call that
never got a row whose payload carried the number in national form
(05550001234), a failed event for a stranger's number, a note with its

## The appointment hardening, second review (2026-10-13)

A re-review of the review fixes confirmed the all-or-nothing draft and the
draft-aware dry run, and found eight more items; each is fixed in its own
commit.

*Refusals cross function boundaries as data.* `agentBookTx` threw its refusals
(`new Error("too-many-changes")`, `"slot-taken"`, the `customer-busy:` and
`lead-time:` sentences), and a message thrown in a mutation reaches the
calling action as "Uncaught Error: …\n at handler …" (`performAsyncSyscall`
re-wraps it). So on every live booking `message === "too-many-changes"` in
`http.ts` and the chat lane's `bookingRefused` never matched: no handover
email, no escalate note, and `nearest_free` never appeared; the agent was
handed the stack. Drafts only worked because they catch inside their own
transaction. `bookingProblem` now returns `{ code, note }`, `voiceBook` returns
`{ ok: true, … } | { ok: false, code, note }`, and both lanes branch on the
code and give the model the note. The sweep for the pattern (an error's text
compared after crossing `runMutation`/`runQuery`/`runAction`) found no other
decision made that way in `convex/`; the frontend's `raw.includes("code")`
checks survive the framing and stay. Three places handed a crossed error's raw

model), a failed bulk dial's stored reason and a failed provisioning job's.
AGENTS.md gains the rule as its third Convex trap.

*cal.com hears about a booking only once it will stand.* The parked cal.com

*A refused line no longer wedges an agent's setup.* The bind-time

number still on it. `begin` resumes that job, and once its agent exists it
never edits the number; the form resends it, and `begin`'s own early check
refused it too. So every retry hit the same refusal, the agent never

*Every phone handover has an owner.* The older-engine guard (`just-changed`,
template < 14, three minutes after a change) told the caller a colleague
would be in touch and emailed nobody, unlike the cap and the calendar errors
beside it. It now queues the same `cancelNeedsPerson`/`moveNeedsPerson`
alert, naming the appointment that engine would have acted on.

*A repeat never meets the cap.* Both lanes refused `too-many-changes` from
`ownNext.changesToday` before the change ran, so at the cap a provider retry
or a second "yes" for a cancel already made was answered as a handover (and
emailed the team) instead of "already cancelled". The transaction always
recognised the repeat before counting (`ownTarget`); the lane checks are

*A start minute is not an appointment.* Two orders for 10:00 share a minute,
and `ownTarget` took whichever row came first, so a repeated cancel of the

`appointment_services` beside `appointment_start` (find_appointment and

parameter), and the target is the open row at that minute with those

now shared with the older-engine guard). Otherwise the tool answers

*The chat assistant stays quiet only when the confirmation will reach the

*İPTAL typed twice cancels one appointment.* A typed EVET or İPTAL fell back

next upcoming one is used only when it is the only one; with several nothing

owner alert has already gone). A confirm is only ever pointed at an open
appointment. Verified by reading: this path schedules sends and alerts.

## Bulk calls keep to opening hours, skip who they should, and say what happened: P6b (2026-10-17)

calling hours, a "now" waits for them), ac5988a5 (a bulk call skips anyone

**A run rings only while the business is open.** Nothing in the call chain

minute it opens. The hold lives on the run and is read in the claim's own
transaction because the reaper restarts every running run every five minutes

would have been dialled straight through. The reaper now leaves a run alone

the network (red, the call card's sentence on hover) and never Sent for a
call; the call card learned the refusal codes and reads every `error_` code
as a call error. The activity report counts answered by the code and adds a
voicemail count, and each call in a customer's history carries its `result`.

**Nobody already booked or already called that day is rung.** A run took
everyone ticked, in order, whatever had happened to them since the tick: a
customer who booked by WhatsApp while waiting in line was still rung, and so

consent and no-AI-calls checks: an open booking still ahead of them (the
booking page's own reading of upcoming, an open ASAP order included) skips

one waits and sees the other's call). A call that never reached their phone

calls and every inbound call draw on it) marked a customer as tried whose
phone never rang, and a call the provider ended with

later try can pass (`lib/callOutcome.isRetryableDialError`: a 429, a 5xx, or a
full pool named in the body, Nudge abbbbdff's test) and a call ended with

Trying again at 10:42." on the run and "Trying again shortly" on the

## 2026-10-18 — Nudge port P36: requested callbacks

A caller who asks to be rung back at a time they name now gets that call,
once. Nudge does it with trigger rules over `call_back_time`; Resepta has no
triggers, so it is one built-in behaviour (`convex/callbacks.ts`, table
`callbacks`), and every guard a bulk call obeys is re-read in the claim:
open hours with a hold until opening, consent and No AI calls, the demo org,
another automated call ringing them, the operator's limit, the agent and its
line, the published version, refusals for want of a line requeued six
times. How it runs is in `docs/subsystems.md` → "Requested callbacks".

Decisions, made here:
- **Capture is a post-call analysis field, template v16.** Like v15's
  no-AI-calls flag it reaches existing agents through Update, and a call
  mid-conversation tool would have been a new tool definition every older
  agent lacks. The prompt line asking for a time reaches new agents only;
  the analysis reads the transcript either way.
- **Only an answered call, and only a time.** "Call me later" queues
  nothing: a callback rings a real phone, so a guessed time is worse than
  none, and the call card still shows what was said.
- **The time is moved, never refused, for closed hours** (to the next open
  minute, and the card says so), refused when gone, unreadable or more than
  30 days out. Never sooner than five minutes after the call.
- **One call, not Nudge's three chances.** A callback that rings out shows as
  a missed call on the record; a person decides whether to try again. The
  bulk run's "already called today" skip does not apply: this call was asked
  for.
- **The operator's limit now counts callbacks and bulk items together**, on
  both sides, since both are automated calls on the one shared account.
- **Cancel is any member's**, with no confirm: stopping a call is never the
  risky direction.

Owed: Update to v16 per business, then one real callback end to end (the
analysis resolving "tomorrow" against `{{now}}` is the part only a real call
can prove; if the provider does not substitute variables in an analysis
description, the field still has the transcript's own words to go on).
